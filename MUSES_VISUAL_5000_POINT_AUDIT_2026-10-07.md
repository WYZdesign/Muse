# Visual Design Audit — 5,000 Points

**Audit date:** 2026-10-07
**Evidence baseline:** branch `claude/restore-pending-fixes` at `5abd049` (built on `origin/main` at `c8eff22`); production site `https://muse.wyzdesign.com` (DOM-level check only — live screenshots could not be captured this round, see "Methodology and limits" below); every finding below is cited to a file and line.
**Scope:** this audit follows the same 25-domain × 4-subcategory × 50-point structure as `MUSES_BOARDROOM_5000_POINT_AUDIT_2026-10-04.md`, narrowed specifically to **visual design** — styling, theming, layout, responsive/native rendering, and the correctness of what the UI visually displays against what the backend actually provides. It does not re-score business/ops/security domains that audit already covers.

## Methodology and limits

This audit combined two approaches: (1) direct code inspection of `muse.css` (~2,700 lines), every screen/component/modal under `src/app/(muse)/muse/`, and every backend handler under `src/lib/muse-actions/`, cross-referencing what each screen renders against what its backend `.select()` actually returns; (2) a live DOM check of the production Discover screen (`get_page_text`, not a screenshot — see below) confirming real, populated profile cards are serving in production, not an empty/demo-only feed.

**What this audit could NOT do:** live pixel screenshots of the deployed app. The browser pane on the connected device returned real DOM text successfully, but every `screenshot` call timed out with "the page did not finish rendering in time... Claude's window may be behind another window" — the window was backgrounded on the user's desktop, which stops the renderer from drawing a frame to capture. This means every finding below is **derived from source code**, not visually confirmed on a live render. Treat "cosmetic" and "inconsistency" severities as high-confidence (CSS values either match or they don't — no judgment call that a screenshot would change), but treat anything claiming a specific *rendered* visual outcome (e.g. "this would clip," "this reads as low-contrast") as needing a real-device or screenshot pass to fully close out — flagged per-finding where relevant. One finding (#21) was a genuine **confirmed bug** (backend never selected the columns the UI reads), verifiable from code alone with no rendering required, and has already been fixed and tested as part of this audit (commit `5abd049`) rather than merely documented.

## Executive score

**Current score: 3,370 / 5,000 (67.4%)**

The visual system has real bones — a 12-theme token system (6 dark, 6 light) with a working user-facing toggle, a consistent toast/error pattern, consistently-used `EmptyState` component in most places, and clean `next/image` `sizes` usage on every `fill` image found. What pulls the score down is adoption, not design: hundreds of inline hardcoded colors bypass the token system (and visibly break in light themes), there's no shared spacing/radius/button-padding scale so near-identical elements (card radius, button padding, status pills, avatar sizes) drift across the app with no single source of truth, and one confirmed data-binding bug silently disabled two trust signals (verified checkmark, online dot) for every real user. None of this is a redesign — it's consolidation of patterns that already exist in one place or another into the token system that's already built.

## Scoring rubric and subcategories

Each domain is worth 200 points, scored as four 50-point subcategories: **consistency** (is there one defined pattern, not several competing ones), **implementation** (is the pattern actually applied where it should be), **correctness** (does it match what the backend/data actually provides, where applicable), and **verification** (is there a test, a documented baseline, or a live check confirming it — vs. untested assumption). No domain may be called 10/10 until all four are evidenced, same discipline as the boardroom audit.

## Detailed findings by domain

### Design system foundation (1–6)

**1. Color tokens.** `muse.css`'s `:root` (line 3) defines ~35 reusable color tokens. Despite that, 337 raw hex-literal colors were counted across `screens/*.tsx` against 815 `var(--...)` references — a real but partial adoption gap, concentrated in `color: "#fff"` literals (64 instances) where `var(--text)` already expresses the same thing: `screens/BtsScreen.tsx:334,618`, `screens/CodexScreen.tsx:115,184,204`, `screens/CommunityScreen.tsx:330,393`, `screens/DiscoverScreen.tsx:458,661,787`, `screens/ChatScreen.tsx:363,386`.

**2. Theming.** Not a dark-only app — `muse.css:1508-1529` defines 12 full themes (6 dark: lasunset/deepspace/nebula/deepsea/cinder/boreal; 6 light: sunrise/daylight/sky/rose/meadow/frost) via `[data-theme]`, with a working picker at `SettingsScreen.tsx:30-32,753-772`. The hardcoded literals from #1 don't participate in this system: `color:"#fff"` in `DiscoverScreen.tsx:458/661/787` and `CodexScreen.tsx:115/184/204` will render white text even under a light theme — a genuine functional break for anyone using `sunrise`/`daylight`/etc., not a cosmetic nitpick, since the toggle is live and user-reachable today. One class of hardcoded value (`.modal-header`/`.modal-body` background `#170a28`, `muse.css:1056,1060`) does get a correct light-theme override at `muse.css:1613-1614`, proving the pattern is known for CSS classes — it just doesn't extend to inline-style literals in `.tsx` files, which have no equivalent override path.

**3. Typography.** Font-family split (Inter for UI/body, Playfair Display italic for ~15 display-heading selectors like `.hero-text`, `.match-title`, `.card-hero-name` at `muse.css:2168`) is clean and consistent. No defined type scale exists: ~30 distinct `font-size` literals in `muse.css`, including odd half-pixel steps (9.5px, 11.5px, 12.5px, 13.5px, 37.5px) alongside a reasonable 11–14px cluster for body text. Truncation guards are thin — only 10 selectors use `text-overflow:ellipsis`; `.card-hero-name` (24px Playfair) and `.profile-name` (26px) have none in their own rules, so a long display name has no defensive wrap/clip handling (not confirmed broken without a live render — flagged for a real-device check).

**4. Color contrast.** No dedicated contrast-testing baseline exists in the test suite (checked `tests/` and `KNOWN_A11Y_GAPS` — only a screen-reader `announce()` helper, no contrast logic). Two specific issues are already documented in prior informal audits and appear unresolved: a low-contrast "Later" dismiss button on the daily-streak modal reading as disabled (`CHATGPT_MOBILE_OVERLAY_MODAL_BUNDLE_2026-09-21.md:12`) and a low-contrast Network-screen subtitle/search placeholder over an animated background (`CHATGPT_MOBILE_AUDIT_HANDOFF_2026-09-21.md:24`). Not re-derived here — citing the existing record per this repo's own "don't re-verify what's already documented" convention.

**5. Spacing & radius.** No `--radius-card` or spacing-scale token exists. Card radius alone has 7 distinct values for conceptually similar containers: `.swipe-card`/`.card-border` 24px, `.match-card`/`.conn-card`/`.moments-card` 20px, `.brief-card`/`.tier-card` 22px, `.match-card-grid` 16px, `.quest-card` 14px, `.tour-card` 26px, `.card-photo-thumb` 10px.

**6. Buttons.** No `--btn-padding` scale; 8 distinct padding patterns sampled across `.btn`, `.auth-social-btn`, `.conn-btn`, `.match-btn`, `.tier-btn`, `.btn-sm`, `.btn-xs`, `.quest-filter-btn`, clustering loosely around 8–18px with no consistent step. See domain 25 for the separate (and largely resolved) native-`<button>`-element migration.

### Component consistency (7–13)

**7. Modals.** Most modals share a `modal-header`/`modal-back`(FiArrowLeft)/`modal-close`(FiX) pattern (`GuidelinesModal.tsx:12-15`, `UnmatchModal.tsx:25-28`, `ReportModal.tsx:48-51`), but three real exceptions exist in the same directory: `SelfDiscoveryModal.tsx:99` hand-rolls its own inline-styled close button instead of the shared class; `ShareProfileSheet.tsx` (entire file) is a bottom sheet with no header/close pair at all — only a full-width bottom "Close" button or backdrop tap; `EditProfileModal.tsx:74-77` has a back arrow but no close button, just an empty spacer div. Users get three different exit affordances across modals that otherwise look equivalent.

**8. Badges/chips/pills.** Status pills (Pro, TFP, Paid, Open Call, 18+) have no shared variant component — `CollabScreen.tsx:305-310` and `CommunityScreen.tsx:363` each independently hardcode near-identical pill patterns with their own inline color triples; `NetworkScreen.tsx:850` and `:1621` hardcode the *same* "Pro" badge twice in two different functions in the same file rather than sharing one constant. Only the `border-radius:99px` convention is consistently followed. (The "verified" badge color drift specifically — gold in some places, green/blue in others for conceptually different verification types — is covered under domain 21/23 since it's a correctness question, not just a styling one.)

**9. Avatars.** At least 9 distinct hardcoded circular-avatar sizes for the same semantic role: 128px (`ProfileScreen.tsx:243`), 88px (`EditProfileModal.tsx:82`), 80px (`MatchOverlay.tsx:67-68`), 60px (`IntentPickerModal.tsx:42`), 52px (`FeedScreen.tsx:375,539`), 48px (`LikeNoteModal.tsx:54`, `post/[id]/page.tsx:52`), 40px (`ChatScreen.tsx:280`, `MenuModal.tsx:47`), 36px (`FeedScreen.tsx:633`), 32px (`StoryViewer.tsx:24`), 30px (`FeedScreen.tsx:739`) — no shared size-scale class.

**10. Alt text & image fallback.** `FeedScreen.tsx` is the clean reference pattern: descriptive alt text (`${post.author}'s avatar`, `FeedScreen.tsx:539`) plus `onError={handleImgError}` on every `<Image>`. Elsewhere, generic alt text recurs (`alt="Avatar"`: `EditProfileModal.tsx:82`, `ReferralPanel.tsx:133`, `MyAlbumsManager.tsx:260`, `StoryViewer.tsx:24`, `IntentPickerModal.tsx:42`; `alt="Photo"`: `StoryViewer.tsx:22`, `post/[id]/page.tsx:60`). One real gap: `CollabScreen.tsx:277`'s brief-author avatar `<Image>` has no `onError` handler and no placeholder — a brief authored by a profile with no avatar can render a broken image with no graceful fallback, unlike every other avatar render in the app. Not fixed this round (adding `handleImgError` here means threading the prop through `CollabScreen`'s signature and its call site in `page.tsx`, a slightly bigger change than the one-line fixes made elsewhere this round) — flagged as a ready-to-pick-up follow-up.

**11. Loading states.** Shared `ScreenSkeleton` component (`src/components/ScreenSkeleton.tsx`, documented with a file-purpose header as of this session) is imported by exactly one screen (Feed). `SessionsScreen.tsx` and `BtsScreen.tsx` have zero loading/isLoading/spinner references anywhere — on a slow fetch these likely show a blank gap, not a skeleton. Other screens (`DiscoverScreen.tsx:393/405`, `ProfileScreen.tsx:394`) handle loading with their own one-off inline markup rather than the shared component.

**12. Empty states.** Genuinely well-adopted: `EmptyState` (icon+title+sub, `muse.css:641` `.empty-state`) is used consistently in `MusesScreen.tsx:360/400`, `CommunityScreen.tsx:524/527`, `SessionsScreen.tsx:407/525/600`, `CollabScreen.tsx:245/249`, `FeedScreen.tsx:508/510`. Several secondary screens bypass it with plain text-only divs instead: `MenuModal.tsx:390,411` ("No saved quests yet."/"No bookings yet."), `SettingsScreen.tsx:1353,1386`, `PaymentHistory.tsx:133`, `CommunityRulesEditor.tsx:78`, `SafetyCheckinModal.tsx:338`, `PromptBankModal.tsx:143`, `BoostAnalyticsPanel.tsx:112/164`.

**13. Error/toast.** Clean, single mechanism: `showToast` prop threaded through screens, funneled via `useToastChannel.ts` (`muse:toast`/`muse:storage-quota` window events) into one toast UI. No instance found anywhere of a raw `error.message`/`err.message` rendered directly to a user — error text is consistently human-authored and passed through `showToast` (e.g. `FeedScreen.tsx:234` maps camera error names to friendly copy).

### Responsive & native (14–20)

**14. Breakpoints.** At least 4 distinct small-screen cutoffs with no shared constants: 340px (`muse.css:450`), 360px (`muse.css:2483`), 390px (`muse.css:432,593`), plus the one real layout breakpoint at 767/768px used widely. A device at ~375px (iPhone SE/mini-class widths) falls between the 360 and 390 rules and may get neither adjustment — not confirmed broken without a real device, but a plausible gap given the gridlines chosen.

**15. Safe-area insets.** Applied to `.phone`, `.nav` (bottom tab bar), the hamburger panel, and `.chat-header`. Not applied to the Discover match-action FAB (`DiscoverScreen.tsx:705-711`, `.match-fab` at `muse.css:2237`, fixed `position:absolute;bottom:28px` — a static offset, not inset-aware) or to `.modal-header`/`.modal-close`. `muse.css` itself documents a known double-padding conflict between `.phone` and `.chat-header` (comments at lines 1112, 1383-1390) — i.e. this is a tracked, not newly-discovered, rough edge.

**16. Viewport units.** `muse.css` is internally consistent — every `100vh` is paired with a `100dvh` override (lines 221, 1026, 1397). Eleven other files use bare `100vh` with no fallback: `src/app/dmca/page.tsx:13`, `post/[id]/page.tsx:48`, `admin/ModerationPanel.tsx:194`, `admin/page.tsx:131`, `profile/[id]/page.tsx`, `reset-password/page.tsx`, `not-found.tsx`, `terms/page.tsx`, `privacy/page.tsx`, `safety/page.tsx`, `global-error.tsx`. Most are secondary/static pages, but `post/[id]` and `profile/[id]` are public deep-link pages plausibly opened in mobile Safari or an in-app browser, where bare `100vh` is the classic address-bar-resize bug.

**17. Touch targets.** Primary controls are generally fine: `.modal-close` 44×44 (`muse.css:1062`), `.hamburger-close` 42×42, Discover's match-radial actions 44×44 (`DiscoverScreen.tsx:707-711`). Secondary icon-only controls run smaller: `.album-thumb-remove` 22×22 (`muse.css:2158`, a photo-delete "x" in `MyAlbumsManager.tsx:244` — the sharpest risk since it's a destructive action on user content), `.premium-popup-close` 24×24, `.hamburger-bell` 36×36, `.hsc-arrow` 18×34 (horizontal-scroll nav arrows).

**18. Horizontal scroll / fixed-width.** Clean. Scroll rows correctly use `white-space:nowrap;flex-shrink:0` (the intended pattern, not a bug). Card/modal containers use `max-width` + `%` bases, not rigid fixed px widths, so they shrink correctly below 375px. Only fixed-px elements found are absolutely-positioned decorative background orbs, which are overflow-clipped and not a real risk.

**19. Image `sizes` / CLS.** Clean. Every `fill`-mode `<Image>` usage found includes an appropriately scaled `sizes` prop (e.g. `PublicProfileScreen.tsx:218,471,509`); zero instances found of `fill` without `sizes`.

**20. Capacitor/native.** `capacitor.config.ts` correctly configures `StatusBar` (dark, `#0a0612`), `Keyboard` (`resize:"body"`, dark style), `SplashScreen`, and iOS `contentInset:"automatic"`. No CSS or component-level `Capacitor.getPlatform()`/body-class branching exists beyond that static config — acceptable for now, but means no distinction between iOS and Android gesture-nav/home-indicator spacing beyond what `env(safe-area-inset-*)` handles uniformly.

### Visual ↔ backend correctness (21–24)

**21. Discover-card correctness — confirmed bug, fixed this round.** `DiscoverScreen.tsx:488-489` renders a verified checkmark and an online dot from `profile.verified`/`profile.online`. `get.ts`'s `discover-ranked` handler's `.select()` (the only handler backing this exact screen) never fetched `verified` or `last_seen_at` — every sibling handler serving a profile card (`matches`, `feed`, `profiles`, `sessions`) does fetch both. Both signals were unconditionally `false`/`undefined` for every real profile object, working only on the static demo deck, which is exactly why this stayed invisible through demo-mode QA. **Fixed as part of this audit** (commit `5abd049` on `claude/restore-pending-fixes`, not yet merged to `origin/main`): added both columns to the select, derived `showOnline` the same privacy-preference-respecting way `showAge` already was (rather than leaving it unset, which would have silently ignored a user's own "hide my online status" choice), and added the matching `online` derivation (5-minute last-seen threshold, same as the existing matches-list logic) on the frontend. Two new regression tests lock this in. Domain score reflects that this was live-broken until today, not that it's unresolved now.

**22. Feed/Collab/Community correctness.** Clean on the two specific counts checked: brief applicant counts (`get.ts:254` selects `muse_brief_applications(count)`; `normalizers.ts:74-91` correctly unwraps the PostgREST `[{count:N}]` array shape; consumed at `CollabScreen.tsx:288,297-299`) and community member counts (`communities.ts` keeps `member_count` current on join/leave; `normalizers.ts:48` maps it with a safe `?? 0` default; consumed at `CommunityScreen.tsx:336,361,548,555-556`). No stale-default or silently-missing-field pattern found in either.

**23. Other field-name/count correctness.** No stale frontend/backend field-name mismatches (e.g. frontend reading `imageUrl` while backend returns `avatar_url`) were found in the screens sampled (Discover, Collab, Community, Muses, Profile, Feed) beyond the verified/online gap in #21. This is a **sampled check across 6 screens, not an exhaustive one** — the same class of bug could exist in an unsampled screen (Sessions, Events, Chat, Studios were not cross-referenced this round) — listed under "Known open issues" below rather than scored as fully clean.

**24. Entitlement-gated visuals.** Clean and backend-enforced. `MusesScreen.tsx:367`'s `unlocked = isPaidTier(currentUser.tier)` reads a genuinely server-selected `tier` column (`shared.ts:144`); `profile.ts`'s own test suite (`profile.test.ts:38-40`) confirms any client-supplied `tier`/`verified` field is stripped before a profile write, so a client can't self-grant the unlocked visual state. No client-only-guess paywall logic found.

### Accessibility migration status (25)

**25. Native-control migration.** Across three earlier rounds this session, ~26 `div`/`span[role="button"]` elements were converted to native `<button>` in 14 files, each verified to keep its original visible content/accessible name (no regression introduced by the conversion itself — checked this session by diffing every converted element's rendered children against its pre-conversion content). 12 files still show `role="button"`, and every remaining instance was checked and falls into one of four deliberate, documented deferral categories: Image-`fill` grid cards (converting risks a visual shift from native `<button>`'s default padding without a way to screenshot-verify here), invisible absolute-positioned tap-zones, one intentional div (avoids an axe `nested-interactive` violation since it already contains a real nested `<button>`), and unlabeled visual-only progress dots. None are overlooked — all are either genuinely risky to convert blind or correctly left alone.
