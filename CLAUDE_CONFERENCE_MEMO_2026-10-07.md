## Three findings the other agents likely missed

1. **Sessions browse shows the wrong name on every real listing.** `muse_sessions` has no `name` column — it's the host's name, `title` is the session's. The card headline, booking-confirmation toast, aria-label, and modal title all read `s.name`, but `get.ts`'s `sessions` handler never joined it, so `normalizeSession()`'s fallback (`s.name ?? s.title`) silently showed the session's own title a second time instead of the host's identity. This is the kind of bug that's easy to miss in a live click-through unless the tester happens to know the real host's name doesn't match what's displayed — a static code cross-reference caught it, browser evidence likely wouldn't without that prior knowledge. **Fixed, with a regression test** (`dddf658`).
2. **Live voice/video notes vanish mid-chat.** A voice/video note received via Supabase realtime while the recipient's chat is open renders as a blank bubble with no player — the realtime relay forwarded only `img`, dropping `kind`/`media_url`/`media_type`/`duration_ms`/`transcript`. It only looks right after a reload, because the reload path (`fetchConversationHistory`) already mapped those fields correctly. This needs two accounts open simultaneously exchanging a media message in real time to surface — a narrow enough interaction that it's genuinely easy for any single-tester audit pass to miss. **Fixed, with regression tests** (`dddf658`).
3. **The public pricing page oversells features that are already free.** `/muse/pricing` lists "Advanced search filters" and "Portfolio analytics" as Pro-exclusive, and claims a 5/week connection-request cap for free accounts. Code reality: `AnalyticsScreen.tsx` has zero tier checks anywhere — any free user already has full portfolio analytics; search filters are likewise ungated anywhere in `DiscoverScreen.tsx`; and `connect.ts`'s rate limit is a flat per-IP cap with no tier branch at all, so the stated "5/week" free-tier limit isn't enforced for anyone. This sits at the seam between the "Landing/Payments" domains in the new 25-domain taxonomy, which is probably why neither audit isolated it as its own line item before now — it only surfaces by cross-referencing a *marketing* page against *backend enforcement*, a combination neither of our taxonomies explicitly names as one check. **Not fixed** — documented, needs a product call (gate the features for real, or fix the copy) before it's acted on blind.

## Five highest-leverage fixes, ranked by user impact × implementation risk

1. **Pricing page oversell (above, #3).** Highest impact — direct exposure to paying customers and outside scrutiny (a subscriber or journalist could notice). Low-to-medium risk: either flip a boolean gate on two screens, or edit three lines of marketing copy. This is the one I'd act on before any paid-tier promotion goes out.
2. **Demo-mode truthfulness / console-visible 409s and 401s** (Codex's finding, credited — I haven't independently re-verified this live). High impact on trust once a waitlist/invite wave starts clicking around; medium risk because it needs a per-action decision (disable vs. label "founding beta" vs. leave as-is) rather than one global switch.
3. **Weekly-login pips desync from the real streak number** (`StreakWidget.tsx`'s 7 day-pips are pure `localStorage`, never cross-checked against the server, sitting right next to a streak *number* that IS server-synced). Low risk, cheap to fix (either wire the pips to a real server record or remove them) — ranked here because it's the cheapest win on this list, not the most severe.
4. **Network/Professionals search schema mismatch** — the search box returns `muse_profiles` rows into a UI built for `muse_professionals` rows, rendering broken photos and literal `undefined` stat tiles. High impact for anyone who actually searches; higher risk than the above because it needs an actual data-model decision (query the right table vs. build an adapter), not a one-line patch.
5. **Onboarding's unconditional "Welcome to Muses!" toast** — fires regardless of whether the profile save, referral apply, or portfolio-photo-add calls actually succeeded, so a new user with a flaky connection can lose their referral code and photos silently with zero retry affordance. Ranked last only because it's a narrower failure window (needs a request to actually fail mid-onboarding) than the others, not because the consequence (silent data loss on day one) is minor.
